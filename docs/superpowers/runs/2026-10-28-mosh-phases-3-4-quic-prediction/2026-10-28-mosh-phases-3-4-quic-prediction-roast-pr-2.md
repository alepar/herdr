(new; lanes: premortem, hot-path-perf, concurrency-async) [lanes: premortem, hot-path-perf, concurrency-async]
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: keeper.rs:911-920 at head 35354fa9: `if !session.ring_backlog.is_empty() { drain_ring_backlog(session); shared.kick.notify_all(); if !session.ring_backlog.is_empty() { table = shared.kick.wait(table)...; continue; } }`. `drain_ring_backlog` (keeper.rs:1001-1010) returns at once when `source_room()` is 0 (`if n == 0 { return; }`), yet the notify still fires. `kick` is one Condvar shared by every session (Shared.kick, keeper.rs:102). No other `kick` waiter notifies on a wake with nothing to do: `leg_writer` uses `wait_timeout` (880) and never notifies; the waits at 918 and 938 just re-wait. Spin trace: reader A drains 0 bytes, notifies, waits (releasing the mutex); reader B parked at 918 wakes, drains 0 bytes, notifies A, waits; repeat with no timeout or backoff, each round taking the global table mutex that run_leg, leg_writer and the main loop need. A lone stuck reader cannot wake itself, so it needs two or more stuck sessions in one keeper (keeper_hash in remote/mod.rs:218 keys the keeper per uid/server socket, so several clients on one host share one keeper). Code is new since the prior head 74768cf2 (d9a78207 replaced the RING_OVERFLOW close with `ring_backlog`); base ended the session instead of waiting. The new tests `render_split_frame_larger_than_the_ring_reaches_a_lane_less_leg` / `_lane_leg` use one session each and cannot show it. Not reproduced at runtime by any seat; all three traced it from source.
