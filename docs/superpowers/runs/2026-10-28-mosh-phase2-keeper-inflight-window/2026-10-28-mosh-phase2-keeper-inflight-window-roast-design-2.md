## Rejected (with reason)
- §1 coalesced 64 KiB-quantum send record ('a fresh send whose end offset falls in the same 64 KiB quantum as the newest record updates nothing ... read from the record covering that byte') — Later bytes get an earlier send instant, over-reading samples by up to one inter-send gap (62-250 ms), shrinking the window toward FLOOR and failing the §5 0.8 R bound. Rejected 2-1 (ground seat CONFIRM at Nit): §1 'Sampling rate' states the keeper reads full 64 KiB chunks under the sustained flood, so consecutive chunk ends fall in different quanta and nothing coalesces in the steady state the §5 bounds test; partial chunks occur only transiently at window edges; base_rtt and epoch_min are both minima so one aligned sample per epoch avoids a false shrink; at FLOOR (128 KiB, a multiple of 64 KiB) chunks are aligned, so any pin is self-correcting; the finding concedes repeated shrinks are 'not shown'. Surviving Nit from the ground seat: the spec gives no boundary convention between a record keyed by exclusive end offset and lookup by byte ack-1 (exactly aligned ends and a quantum with no chunk ending in it are ambiguous). One-line clarification: key on the last byte (end-1) and name the covering-record lookup; optionally a window.rs unit test with mixed chunk sizes.
- §5 'Window converges' bullet ('a window pinned at FLOOR also satisfies it' with '>= 0.8 * R') — Self-contradiction at R = 1 MiB/s because FLOOR gives ~0.35-0.42 R. Rejected 3-0: 'it' refers to the preceding upper-bound check only; the goodput check is a separately introduced 'Lower-bound sanity' sentence; the §1/§9 FLOOR pin is a production same-leg-RTT-rise tradeoff that the §5 fixed delay line never induces; the controller grows from INITIAL to the ~300-360 KiB needed, inside the 614 KiB upper bound, so the goodput check is a legitimate test of growth. Wording nit at most.
- §1 'Sampling rate' ('below about 320 KiB/s ... may sample rarely and then holds') vs §5 'Supported range R >= 256 KiB/s' — On a smooth real link at 256-320 KiB/s every ACK is a timer ACK, the window holds at INITIAL, and the harness passes only because the §4 line releases whole chunks. Rejected 2-1: DATA frames are atomic, length-prefixed and up to MAX_DATA_CHUNK = 64 KiB (session.rs:30, 257); `delivered()` advances by whole frames and `ack_due` (session.rs:667-672) fires on a 64 KiB advance, so on any real TCP path a completed full frame triggers a byte-count ACK (about one per 250 ms at 256 KiB/s); the 'holds' caveat is scoped to sub-64 KiB bursts; the proposed spike (4 KiB piecewise delivery) tests a pattern the frame layer cannot produce. This re-surfaces the iteration-1 FYI nit '§4 release formula — emulator's whole-chunk release masks the timer-ack sampling hole', spot-rejected then and panel-rejected now. Wording: tie the 320 KiB/s sentence explicitly to sub-chunk bursts.
- §1 epoch rule on a fresh leg ('A new leg resets the controller to INITIAL with no samples') — First qualifying epoch has base_rtt == epoch_min, so q == 0 and the window grows to 320 KiB before it can detect queueing; window above INITIAL at the 2 s Ctrl-C point. Rejected 3-0: the mechanism is real and the spec has no minimum-sample guard, but the finding's own timeline closes epoch 2 at ~1.5 s with a shrink to 240 KiB, below INITIAL before the 2 s mark; the overshoot is a one-off bounded +64 KiB corrected by the 3/4 rule; §5 asserts only the empirical 1.5 s latency and the settled-window bound, never a window <= INITIAL during warm-up; the 'prior report premise' it attacks is not a spec requirement. Note: this is the warm-up slice of the same lag the confirmed epoch-lag finding covers; a sample-count or hold-one-epoch guard addresses both. The iteration-1 rejection of 'Ctrl-C fires before convergence' stands.
