- [Nit] tests/mosh_resume.rs:28 — Round 2 made the outage flood test run on macOS (f8bc7ef1). On macOS `base64` writes one unbroken line, so the Ctrl-C `MARKER` lands at a random column of the pane and splits across two rendered rows in about 1 run in 75. The `client.wait_screen(MARKER, READY)` substring check then times out after 30 s and the test fails intermittently in macOS CI. [lanes: testing]
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Head 85da17f0 drops `#[cfg(target_os = "linux")]` from `a_dense_flood_through_an_outage_stays_in_the_server_socket_and_ctrl_c_answers_after_resume`; ci.yml macos-latest runs `just ci` with the mosh_resume binary. SATURATING_FLOOD (mosh_resume.rs:28-29) is `(trap 'printf "%s%s\n" MA RKER; exit' INT; base64 < /dev/urandom)` in a DENSE_SIZE 400x100 pane. The final assertion `client.wait_screen(MARKER, READY)` is `self.screen().contains(needle)` (mosh_harness.rs:1048-1049) on the ghostty plain-text dump, one line per rendered row. GNU base64 wraps at 76 columns, so on Linux the marker never reaches the pane edge. macOS base64 documents `-b count` with "The default is 0, which generates an unbroken stream" (https://ss64.com/mac/base64.html, fetched by all three seats), so the cursor column at Ctrl-C is effectively random and a marker starting within the last 5 columns splits across two rows. Estimated rate about 1.3-1.4% per macOS run; no seat ran the test on macOS, so the rate is a derivation from the documented default and the per-row screen rendering, not a measurement. Introduced by this round (the test was Linux-only at base b62f8bb5). Severity stays at the seats' Nit: low-rate CI flake in developer tooling, no product behaviour affected.
  fix-shape hint: have the trap print a leading `\n` before the marker (fixes both platforms and keeps the flood portable), or use `base64 -b 76` on BSD / `fold -w 76`; then confirm `wait_screen` cannot see a split marker.
