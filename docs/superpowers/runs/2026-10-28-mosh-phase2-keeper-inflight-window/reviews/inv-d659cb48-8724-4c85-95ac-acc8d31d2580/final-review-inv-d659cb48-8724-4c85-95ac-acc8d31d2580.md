That is consistent with the measured outcome (window pinned at FLOOR, goodput 0.66-0.94 R) and is a candidate cause for the parked goodput follow-up, not a new defect.

Endpoint integration (session.rs). Window reset on set_up and leg_down, ACK fed after validation, fresh_end gates replays from on_send, window-limited raised both when poll_send has bytes and no room and when push_source fills the window (the gap the design's Key abstractions settle). source_room/source_read_size implement §3 (4 KiB round-up while up; exact room while down). The per-send invariant added to the Pair test harness (in flight <= window) is a good guard. On resume the controller's acked baseline is ring.start_offset, not the peer's recv offset; the first post-resume ACK can therefore show a large advance, but record_start (= fresh_end) prevents a replay sample, so this is harmless.

Keeper (keeper.rs). server_reader reads `source_read_size()` bytes; the ACK path already notifies the condvar, so window growth and ACK room wake the reader; leg-up needs no extra kick because room cannot grow at leg-up. Window traces are emitted per epoch snapshot and once at leg-up; FIONREAD and trace I/O run only with a trace dir, but under the global table lock (test-only cost).

Local bridge. The client reader now takes a read size per go signal; while down past INITIAL the bridge still reads a whole chunk so the Phase 1 overflow-ends-session rule stays for the upstream direction (decision mosh-ctt). A go signal of 0 would make `read(&mut buf[..0])` return Ok(0), which the reader treats as client EOF; it is unreachable today only because the caller maps 0 to MAX_DATA_CHUNK.

Cross-task seam: Phase 1 policy reversal. mosh-hex.9 caps keeper source reads at INITIAL while the leg is down. Keeper ring overflow is now unreachable (the RING_OVERFLOW branch in keeper server_reader is dead in practice), and during an outage the server's client writer blocks after about 256 KiB plus the socket buffer. HERDR_MOSH_VISION.md §4.1 ("keeper drain policy", line 79) and known issue 3 (line 247) still describe drain-while-down and ring overflow, and the stated reason for draining (the server control lane has no cap) is answered only in the design note, not by a test of server memory during a long outage. Upstream observer clients have a 30 s send timeout (client_transport.rs OBSERVER_WRITE_TIMEOUT); the keeper relays normal TUI clients, which have none, so no disconnect is expected, but this was not exercised.
