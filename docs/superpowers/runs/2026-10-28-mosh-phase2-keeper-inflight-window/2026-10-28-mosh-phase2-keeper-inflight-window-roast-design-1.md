## Confirmed findings
- [Should-fix] §5 Acceptance test 'Ctrl-C under flood' (`yes; echo <marker>`) — The probe cannot pass as written: an interactive sh/bash aborts the rest of the command list when the foreground `yes` dies of SIGINT, so the marker is never printed and the test times out regardless of the window. The typed command line also contains the marker text, so a screen match could hit the echoed input.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Reproduce seat ran `/bin/sh -i` and `bash -i` under a pty, typed `yes >/dev/null; echo MAR""KER`, sent \x03 after 0.7 s; neither shell printed MARKER, only `^C` and a new prompt. Ground seat cites https://www.cons.org/cracauer/sigint.html ("proper shell" section: discontinue the script when a foreground child dies of SIGINT). design.md lines 127-130 name no trap, no `||`, no prompt detection. Harness panes run SHELL=/bin/sh (bash on this host).
  fix-shape hint: Make the marker survive SIGINT (`yes || echo <marker>`, `trap 'echo <marker>' INT`, or detect the next prompt) and build the marker by expansion or split quoting so the echoed command line cannot match.

- [Should-fix] §5 'No throughput regression' (LAN window grows to >= 1 MiB) with §1 grow rule and Key abstractions 'Gap settled here' — The assertion is likely unsatisfiable under the spec's own control law: on a sub-ms RTT path with a source-bound flood the sender is never window-limited, so the window stays at INITIAL (256 KiB). Window size is also only a proxy for throughput.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: §1 grows only "if the sender was window-limited during the epoch" and "An idle link never grows the window". Key abstractions defines window-limited as "occupancy reached the window". On LAN occupancy is about one 64 KiB ack quantum plus rate x RTT, far below 256 KiB. §5 sizes R at most half the measured flood rate and allows raising the terminal size, which implies a source-bound flood of about 0.5-2 MiB/s. Reaching 1 MiB at q <= 50 ms needs about 20 MiB/s drain. §6 records flood rate, Ctrl-C latency and backlog but no LAN occupancy. No fallback criterion exists.
  fix-shape hint: Add a LAN max-occupancy measurement to the §6 leaf, and replace or back the assertion with throughput parity against the Phase 1 fixed window (within a stated percentage).

- [Should-fix] §1 RTT sampling gate ('takes an RTT sample on each ACK that advances the acked offset by at least ACK_EVERY_BYTES') — On links below about 320 KiB/s, or with sub-64 KiB chunks, the 200 ms timer ACK always fires first, so an epoch can have zero qualifying samples. The spec defines no behaviour for an epoch with no sample, so the window holds at INITIAL on the slow links Phase 2 targets.
  verdict: confirmed (reproduce ✓ / refute ✗-survived — refute seat voted REJECT, outvoted 2-1 / ground ✓)
  evidence: session.rs:669 `ack_due` is `delivered - last_ack_sent >= ACK_EVERY_BYTES` or the 200 ms timer. At R = 256 KiB/s, 200 ms of delivery is about 51 KiB, below 64 KiB. §3 sizes reads to `min(MAX_DATA_CHUNK, window - occupancy)` rounded to 4 KiB, which produces sub-64 KiB chunks near the window edge. Ground seat searched the spec for sample, epoch, empty, no qualifying, fallback: only "an empty deque ... ignored" and "otherwise unchanged". Refute seat's point that full 64 KiB chunks under a sustained flood would trigger byte-count ACKs is conceded by both confirmers as the reason this is not Blocking; it does not remove the unspecified empty-epoch case.
  fix-shape hint: State the empty-epoch rule (hold the window), justify or measure that the harness produces full chunks at R = 256 KiB/s, or fall back to timer-ACK samples with an ack-delay correction; run the proposed spike counting qualifying ACKs.

- [Should-fix] §1 'a bounded deque, at most WINDOW / MAX_DATA_CHUNK entries' with §3 reads 'rounded up to 4 KiB' — The 32-entry bound assumes full 64 KiB chunks, but poll_send and §3's room-sized reads emit smaller chunks (up to 512 records for 2 MiB at 4 KiB). The spec defines no overflow or eviction policy and does not say how overflow affects sampling or epoch closure.
  verdict: confirmed (reproduce ✓ / refute ✗-survived — refute seat voted REJECT, outvoted 2-1 / ground ✓)
  evidence: design.md lines 51-52 state the bound; lines 97-99 size reads to 4 KiB multiples; the Errors line (198) says only that an ACK below the oldest record is ignored, so evicting the oldest silently drops RTT samples, and refusing new records can leave the epoch-closing "first byte sent after the epoch began" without a record. Ground seat searched for evict, overflow, merge, coalesce, record and found no policy. Refute seat's observation that entries are trimmed on ACK does not change the per-chunk count while in flight.
  fix-shape hint: Bound the deque by occupancy in bytes (WINDOW / 4 KiB) or coalesce records per ACK_EVERY_BYTES; track the epoch boundary as a byte offset rather than a deque record; state the behaviour at the bound.

- [Should-fix] §4 'Each chunk read at time t is released at max(t + delay, previous release + len / rate)' — A chunk arriving on an idle line pays no serialization while back-to-back chunks pay full len/rate. base_rtt (a per-leg minimum) can lock onto an idle-chunk sample, so every flood sample reads q >= len/rate (about 250 ms at 256 KiB/s) with no real queue, pinning the window at FLOOR. The §5 convergence test passes on this artifact. [lanes: domain:distributed-systems]
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓ — ground rated Nit)
  evidence: §4 formula as quoted. §1 samples any ACK advancing >= ACK_EVERY_BYTES (64 KiB), and MAX_DATA_CHUNK is also 64 KiB (src/mosh/session.rs:30,34), so a single 64 KiB chunk on an idle line yields a valid sample of about 2 x delay with no serialization term. §5 convergence bound max(FLOOR, 2*R*0.3 s) + chunk is satisfied by a window pinned at FLOOR, and the Ctrl-C bound also passes there, so the tests would not detect the artifact. Ground seat notes the bias reaches base_rtt only when the first chunk after idle is itself the sampled byte, which bounds the severity.
  fix-shape hint: Model the line as depart = max(t, prev_depart) + len/rate and arrive = depart + delay, so every chunk pays serialization.

- [Nit] §1 'base_rtt, the minimum sample on the current leg'; reset only on leg up/down — base_rtt never ages, so a same-leg rise in path RTT above 50 ms (reroute, VPN failover, handover that keeps the TCP leg up) reads as permanent queueing and pins the window at FLOOR until reconnect. The LEDBAT rolling base-delay history is omitted without a stated reason.
  verdict: confirmed (reproduce ✗ — seat voted REJECT, outvoted 1-2 / refute ✗-survived / ground ✓)
  evidence: Ground and refute seats fetched https://www.rfc-editor.org/rfc/rfc6817.html, §2.5: "If the actual base delay increases, however, a LEDBAT sender will take BASE_HISTORY minutes to adapt"; §3.1.1: history exists "To respond to true changes in the base delay, as can be caused by a route change". Both confirming seats searched the spec for aging, rolling, windowed, decay and found none; §9 does not list it as out of scope. Cost is a throughput cap of 128 KiB per RTT, not a latency or correctness failure, hence Nit.
  fix-shape hint: Keep a few one-minute minima for base_rtt, or add one sentence to §1 or §9 accepting the tradeoff.

- [Should-fix] §1 Constants 'FLOOR = 2 * ACK_EVERY_BYTES (128 KiB)' vs §1 Considered 'too large for a 128 KiB/s link'; §5 R rule — FLOOR exceeds the 300 ms BDP on links below about 427 KiB/s. On the 128 KiB/s link the spec uses to reject a fixed window, the adaptive design still holds about 1 s of queue plus about 1.5 s of server-socket backlog, so the 1.5 s Ctrl-C goal is unreachable there, and the acceptance profile (R >= 256 KiB/s) never exercises that regime.
  verdict: confirmed (reproduce ✓ / refute ✗-survived — refute seat voted REJECT, outvoted 2-1 / ground ✓ — ground rated Nit)
  evidence: §1 decrease rule `max(FLOOR, window * 3 / 4)` never goes below 128 KiB. §1 Considered rejects a fixed 256 KiB window as "too large for a 128 KiB/s link". §5 fixes R as "the largest of 256 KiB/s and 1 MiB/s", so no test runs below 256 KiB/s. Main challenges names the ~200 KB socket buffer the keeper cannot shrink. The Goal names no minimum rate. Refute seat's point that the floor is a documented, wire-frozen constraint is accepted by both confirmers as why this is not Blocking; it does not resolve the internal inconsistency or the unstated supported range.
  fix-shape hint: State the supported rate range for the 1.5 s goal (about >= 256 KiB/s), correct the 128 KiB/s wording in §1 Considered, or add a 128 KiB/s evidence point to the §6 leaf.

## Rejected (with reason)
- §5 R rule / Main challenges ~200 KB socket / §6 — Latency budget at R = 256 KiB/s sums to 1.3-1.9 s. Rejected 2-1: R is fixed only after the §6 measurement leaf; at R = 1 MiB/s the same sum is about 0.6 s; the socket backlog is a named, measured, parked tradeoff (D3); a bound failure surfaces as a failing acceptance test before merge. The dissent's arithmetic rests on the 256 KiB/s branch being chosen, which the spec does not state.
- §6 'If the acceptance bound still holds, Phase 2 is done either way' — No decision rule when the bound fails because of the server socket backlog. Rejected 2-1: a failing acceptance test is the normal consequence and the implementer iterates on R, constants or terminal size; §6 and §9 deliberately exclude pacing and SO_SNDBUF; Post-Implementation Notes record divergences. Same theme as the latency-budget rejection above.
- §5 R selection rule — No defined outcome when the flood rate is below 512 KiB/s. Rejected 2-1: the measurement leaf runs first so the shortfall surfaces immediately; the spec names a lever (raise the terminal size); the "rate does not scale with terminal size" premise is speculative. Nit-level wording at most.
- §1 epoch rule with undefined epoch_min — Spurious grow/shrink when an epoch closes with no sample. Rejected 2-1: the no-sample state is defined ("no samples" on a new leg); growth is bounded and corrected by the next sampled epoch; an Option-typed epoch_min is the obvious implementation. The confirmed sampling-gate finding above already asks for the empty-epoch sentence.
- §1 TARGET_QUEUE_DELAY = 50 ms vs 64 KiB chunk serialization — Chunk-size variance trips the 3/4 decrease. Rejected 2-1: base_rtt and epoch_min are both minima and carry the same serialization term in steady flood; a window at FLOOR satisfies every stated requirement; slow-profile throughput is not a spec promise; TARGET_QUEUE_DELAY is confined to window.rs.
- §5 'the test waits until the client output has grown for 2 s of flood' — Ctrl-C fires before convergence. Rejected 2-1: during a 2 s warm-up the window cannot exceed INITIAL; worst case at 256 KiB/s is about 1.3 s, inside the bound; a transient window makes the measurement more conservative, never a false pass; convergence has its own §5 test.
- §2 'poll_send reports each fresh DATA chunk' — Karn's rule rests on unspecified high-water state. Rejected 3-0: send_next only advances within a leg (session.rs:566, 708) and rewinds only at leg boundaries where the deque is cleared; a post-resume send is the first transmission on that leg, so no Karn ambiguity arises.
- Key abstractions 'Gap settled here' (source refused room) — Signal does not fit &self may_read_source and can grow while application-limited. Rejected 3-0: occupancy reaching the window requires a window's worth of unacked bytes, which is not an idle link; growth is +64 KiB per epoch and counteracted by the q > 50 ms rule; &self vs &mut is an implementation detail inside SessionEndpoint.
- Problem description 'single latest-wins render slot' — Premise unverified. Rejected 3-0: src/server/client_transport.rs ClientWriterQueueState has `render: Option<Vec<u8>>` (one slot), `send_ordered` is bounded, only small control messages are unbounded; the §5 end-to-end latency test catches any hidden userspace queue.
- §5 '<= 1.5 s (5 RTT)' wall-clock in CI — No tolerance or retry policy. Rejected 3-0: the margin arithmetic uses the convergence ceiling as the expected value; R is chosen at most half the flood rate; the Perl delay line follows the existing `throttle` knob already running in this harness; flake policy is test-implementation tuning.
- §1 'a sudden flood after idle starts from a small window, not the cap' — Idle leaves a CAP-sized window in place. Rejected 2-1: a window grown to CAP was validated at q <= 50 ms on the same leg; mid-leg slowdown is handled by the 3/4 rule and leg reset; all three seats agree the sentence is overstated, which is a wording fix.
- §3 / Keeper 'server_reader sizes each read with source_room()' — Zero-sized read reads as EOF. Rejected 2-1: the reader is gated by `may_read_source` (occupancy < window) before reading, so room is >= 1 and rounds up to a nonzero size; the shrink case closes the gate rather than producing a zero read.
- §3 reads rounded to 4 KiB while no leg is up — Changes Phase 1 down-leg overflow behaviour. Rejected 3-0: premise false; Phase 1 already overshoots the ring cap by up to 64 KiB while down and reports RING_OVERFLOW (test `down_reads_to_ring_cap_and_overflow_is_reported`, session.rs:1247); 4 KiB rounding narrows the overshoot.
- Walk-through 'ring occupancy never exceeds the window' — False by up to 4 KiB plus shrink race. Rejected 2-1: the push_source assertion is restated against the hard cap, not the current window; the window-limited signal is a >= condition; 4 KiB is about 3% of FLOOR versus the 50% overshoot §3 is written to avoid. Wording nit.
- §6 'Backlog staleness is backlog / R ... 95th percentile exceeds 250 ms' — Decided in advance by R. Rejected 3-0: backlog/R is the true user-visible staleness at that rate; the check only decides whether a parked follow-up is recorded; the spec already names the buffer as the unshrinkable term and lists SO_SNDBUF as the follow-up option.
- §4 delay-line process topology — Shared rate limiter would queue ACKs behind flood. Rejected 3-0: §4 says the line "follows the existing throttle knob's pattern" (per direction); the formula describes one line carrying one flow; the §5 tests would expose a mis-wired shared limiter. Wording nit: say one instance per direction.
- §1 delay-based controller vs competing loss-based traffic — Yields to TCP, pins at FLOOR. Rejected 2-1: a small window serves the latency goal; base_rtt absorbs any pre-existing queue at leg start; fairness and shared-bottleneck throughput are not stated requirements. Ground seat confirmed the RFC 6817 premise and rated it Nit (undocumented tradeoff).
- §1 additive growth +64 KiB per epoch — About 28 epochs to CAP on fast long-haul. Rejected 2-1: bulk throughput on fast long-haul links is not a stated requirement; starting small after idle or a leg reset is an explicit design choice; the cost is a one-time ramp of about 8 s per leg.
- Keeper abstraction FIONREAD / snapshot ownership — No thread or fd ownership specified. Rejected 3-0: the Session struct already holds `server: server.try_clone()?` under the table lock (keeper.rs ~488); the spec assigns snapshot, FIONREAD and trace to the keeper and says LocalBridge emits no trace events; method names and thread choice are implementation detail.
- §2 'While no leg is up, the ring-cap rule is unchanged' — Resume mid-flood replays seconds of stale output. Rejected 3-0: the Goal and §5 cover a live leg only; replay after an outage is Phase 1's resumable-session semantics, deliberately kept; epoch closure and leg reset are defined.
- §1 'A new leg resets the controller to INITIAL' — Post-resume transient of about 0.5 s with no bound. Rejected 3-0: the reset is a stated choice ("a reconnect may be a different path"); INITIAL is 1/8 of Phase 1's fixed window; worst case at 256 KiB/s is about 1.3 s, inside the 1.5 s bound; post-resume latency is not a stated requirement.
- §1 RTT sample vs §2 upstream controller — Large pastes inflate downstream samples. Rejected 3-0: the failure direction is conservative (smaller downstream window, less stale queue); upstream in-flight is bounded by its own window; one-way delay would need a wire change the spec rules out; concurrent upload during a download is outside the stated scope.
- §1 Considered fixed window vs §5 tests (yagni) — Tests cannot distinguish adaptive from fixed small window. Rejected 3-0: the vision doc (HERDR_MOSH_VISION.md line 52, 108) names link-adaptive pacing as the Phase 2 requirement; the §1 rejection also cites "too large for a 128 KiB/s link"; narrow tests are a coverage observation, not evidence the controller is unjustified.
- §5 'With the Phase 1 fixed window the same test must fail the 1.5 s bound' — No branch for a passing baseline. Rejected 3-0: R is at most half the measured flood rate so the 2 MiB window fills and drains in >= 2 s; the baseline leaf runs first; terminal size is the stated lever; the baseline is evidence, not a CI gate.
- §1 base_rtt on a new leg (LEDBAT latecomer) — Absorbs an existing queue. Rejected 3-0: a new leg is a fresh ssh pipe carrying only this session; the first sample comes from the least-queued chunk of the INITIAL burst; replay is bounded by INITIAL and base_rtt is a running minimum that corrects downward; ground seat fetched RFC 6817 and found the latecomer premise does not transfer.
