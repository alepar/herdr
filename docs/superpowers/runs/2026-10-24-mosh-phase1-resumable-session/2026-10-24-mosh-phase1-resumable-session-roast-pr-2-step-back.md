summary: Cluster C1 from the round-1 step-back (session-final teardown) did not hold. Its round-1 local fixes left four members open, produced a fix-regression (r2 local_bridge.rs:1116) and a new flake (r2 local_bridge.rs:2266), and the same weakness turned up at three new keeper and ssh sites in the r2 final review. The decision that owns it is the implementation's teardown model: each endpoint ends a session through inline shutdown, kill and wait calls spread across many sites, with per-site deadlines and an `end_sent` flag set and reset in many places. Replace it with one explicit drain-then-close phase per side.
pattern: Every open teardown finding comes from the same scattered, imperative close path. On the bridge side, a session counts as "done" when bytes reach the pipe, not when the peer has them (r1 [Nit] src/mosh/local_bridge.rs:1065, r2 [Should-fix] src/mosh/local_bridge.rs:2266). The final ACK and the client drain share one ad hoc deadline, and the ACK runs ahead of the drain (r1 [Nit] src/mosh/local_bridge.rs:1096, r1 [Nit] src/mosh/local_bridge.rs:1084; src/mosh/local_bridge.rs:1086, r2 [Nit] src/mosh/local_bridge.rs:1116). On the keeper side, `remove_session` shuts the server stream inline while `to_server` still holds queued bytes (r2 [Must-fix] src/mosh/remote/keeper.rs run_leg — PeerEnd ...). `end_sent` is marked before the write lands (r1 [Nit] src/mosh/remote/keeper.rs:568) and is reset ahead of the removal check (r2 [Must-fix] src/mosh/remote/keeper.rs run_timers ...); grep shows `end_sent` written at 6 sites and `shutdown(Both)` at about 10. On the ssh side, leg teardown waits on the child and joins the stderr thread with no bound (r2 [Must-fix] src/mosh/ssh_leg.rs spawn_leg teardown / local_bridge.rs pre_welcome_failed ...). Round 1 fixed these one site at a time (ca3f68ea, which also touched punch-listed keys), and each fix moved the defect to a neighbouring site. The other open findings are independent: test isolation (cluster C4 carried over), coverage of the on_leg_bytes callers, and Fatal vs Retryable classification.

Only after the drain does it shut sockets and kill or reap the child. Every wait (writer join, child wait, stderr join) is bounded by that deadline. "END sent" is recorded only on write completion, in one place. Removal is decided in one function that is checked before any per-leg state reset.

changes: The teardown implementation in src/mosh/local_bridge.rs (`close_with`, `finish`, `final_ack`, `close_client`, `close_leg`, `kill_leg`, `pre_welcome_failed`, the `end_flush` and `STOP_END_FLUSH` handling in `tick_linked`, `pump_sends` and stop), src/mosh/remote/keeper.rs (`remove_session`, `drop_leg`, `run_timers`, `PeerEnd` handling in `run_leg`, `end_sent` bookkeeping, `server_writer` shutdown) and src/mosh/ssh_leg.rs (`Leg::finish` and the spawn_leg teardown). Today these are many inline shutdown, kill and wait calls with per-site deadlines and flags.
to: One Closing phase per endpoint, with a single deadline (the spec's 500 ms stop budget). Bridge order: drain the client writer, ack up to `client.written`, wait for the leg write to complete and for leg EOF or a peer close, then shut down; the ssh child is killed and reaped once the deadline passes, and the stderr join is bounded. Keeper order: close the `to_server` sender and let `server_writer` drain before shutting down the server stream. `end_sent` is set only when the write completes, and one `should_remove(session)` predicate runs before any state reset. No spec change: the spec already requires ordering after stream bytes, acking only bytes actually written, and "never a hang".
