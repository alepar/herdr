## Confirmed findings            ← consumed by super-design, one task per finding
- [Should-fix] src/mosh/local_bridge.rs:2731 — The new test `client_gone_mid_server_eof_drain_closes_within_stop_budget` (dqw.33) uses `keeper.st().end_written` as its signal to cut the client. That flag means only that the fake keeper's `write_all` of END{server-eof} returned, not that the bridge has read and processed that END. When `stop_reading()` wins the race, the bridge takes the client-EOF path, ends the session as `client-gone`, and the assertion at :2749 that the end line contains `server-eof` fails. [lanes: test-isolation-environment] (new)
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Reproduced twice by the reproduce seat at 913b66cc: the herdr test binary run with filter `remote::attach::mosh::` (default libtest harness, many threads in one process) beside 48 busy-loop CPU hogs failed `client_gone_mid_server_eof_drain_closes_within_stop_budget` (171 passed, 1 failed) with a panic at local_bridge.rs:2749:9, the `end_line.contains("server-eof")` assertion. The scout saw 1 failure in 5 runs under 96 hogs with end line `{"event":"session_end","reason":"client-gone",...}`. Mechanism from source, agreed by all three seats: the fake keeper sets `st.end_written |= is_end_message(&message)` right after `s.write_all` returns (:1914), so END can still sit in the socket buffer or the leg-reader channel. `stop_reading()` is `shutdown(Shutdown::Read)` on the client (:1558). The bridge's client writer gets EPIPE, breaks, and calls `shutdown_client` (Shutdown::Both, :393-396); the armed client reader then reads 0 and sends `Event::ClientEof`. If the main loop handles that before the leg event carrying END, `closing` is still None, `on_client_eof` (~918-928) runs `queue_final_end(CLIENT_GONE)`, and `begin_server_eof` later returns early because `closing.is_some()`. Nothing in the bridge orders a client death against an END still in flight, so the product behaviour is valid and the test is wrong. The race was not reproduced in nextest-style one-process-per-test runs (100/100 alone under load), so the CI exposure is low; plain `cargo test` is exposed under load.
  severity note: seats split 2-1 (reproduce Should-fix, refute Nit, ground Nit). Final severity Should-fix, profile-independent: the test asserts an ordering the bridge does not promise, so it is an incorrect test rather than a slow one; the failure was reproduced by two independent parties; and iterations 2 and 3 rated the analogous ordering flakes in this same test family (:2266, mosh_integration.rs:169) Should-fix. A flaky test taxes every later change regardless of blast radius.
  fix-shape hint: wait on a bridge-side signal that Closing(ServerEof) has begun (a trace event or a test seam on the bridge state) before `stop_reading()`, instead of on the keeper-side `end_written`; the same rewrite is the natural place to fix :2716 and :1558 below.

- [Should-fix] src/mosh/local_bridge.rs:1558 — `client_gone_mid_server_eof_drain_closes_within_stop_budget` relies on Linux AF_UNIX semantics: the client's `shutdown(Shutdown::Read)` is expected to make the bridge's blocked writer fail with EPIPE. The test module is unix-only, not Linux-only, and runs in the macos-latest CI lane; on XNU a peer's SHUT_RD does not set SS_CANTSENDMORE on the sender, so the bridge writer gets no EPIPE and the test either times out at its 3 s `session_end` wait or fails on `!acked_all`. [lanes: testing] (new, external claim grounded by all three seats)
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Internal facts (read at 913b66cc): the tests module is `#[cfg(all(test, unix))]` (:1394); `stop_reading` (:1558-1561) only calls `shutdown(Shutdown::Read)` on the client end and is used only by this test (:2734); its doc comment says "the bridge's writer fails with EPIPE". ci.yml:57-62 runs macos-latest with kind unix and nextest_filter `not binary(live_handoff)`, and :177 runs `just ci-tests` with that filter, so this test runs on macOS. External facts, fetched independently by all three seats from https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/kern/uipc_socket.c and .../bsd/kern/uipc_usrreq.c: in `soshutdownlock_final`, SHUT_RD only calls `sorflush(so)` on the socket's own receive buffer (`if (how != SHUT_WR) sorflush(so)`), and `pru_shutdown` runs only when `how != SHUT_RD`; only `uipc_shutdown` calls `socantsendmore(so)` and `unp_shutdown` (which calls `socantrcvmore` on the peer), and that path is SHUT_WR-only; `uipc_send` returns EPIPE only on the sender's own `SS_CANTSENDMORE`. So on macOS the bridge-side writer never sees EPIPE; its 20x60 KB writes to the paused client either block (Phase A waits out the 30 s grace, the 3 s `session_end` wait panics) or are dropped and counted as written (`written >= frames_end`, everything acked, `!keeper.st().acked_all` fails). On Linux `unix_shutdown` gives the peer SEND_SHUTDOWN, which is why the test passes there (0.59 s on Fedora). Nobody ran the test on macOS; the lack of EPIPE is grounded in kernel source, the exact failure mode is inferred. The ground seat notes the seats' WebFetch summaries paraphrased the kernel source, so the quoted lines are close paraphrases, not verbatim.
  severity note: unanimous Should-fix. Test-only portability defect that likely turns the macOS CI lane red (fail-fast is false, so the other lanes still run). Not demoted: a red CI lane blocks merges regardless of the product's blast radius.
  fix-shape hint: cut the client by dropping it (full close) or with `shutdown(Both)` instead of SHUT_RD, or gate the test with `cfg(target_os = "linux")` if the SHUT_RD-only shape is essential; confirm on a macOS runner with `cargo nextest run -E 'test(client_gone_mid_server_eof_drain)'`.

- [Nit] src/mosh/local_bridge.rs:2716; src/mosh/local_bridge.rs:2718 — The dqw.33 regression test `client_gone_mid_server_eof_drain_closes_within_stop_budget` never exercises the `client.writer.is_finished()` arm of `client_drained()` it was added to guard: the bridge's client writer shuts the socket Both on EPIPE, the armed reader sees EOF and sets `client_eof_seen`, so mutating `is_finished()` to `false` leaves all tests green, and the parked-reader case where only `is_finished()` ends Phase A has no test. [lanes: testing, test-causality-lifecycle] (new)
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Two independent scouts ran mutations at 913b66cc in detached worktrees: `client.writer.is_finished()` -> `false` (:1194): the test still passes (0.59 s), whole mosh:: suite 172/172 on 6 of 6 runs; `|| self.client_eof_seen` -> `|| false` (:1192) alone: still passes; both mutated: the test fails (wait_until panic after 3.05 s). So each arm is redundant under this test and neither is guarded on its own. Mechanism, confirmed from source by all three seats: the client writer thread (~853-870) breaks on the first write error and calls `shutdown_client(&stream)`, which is `shutdown(Both)` (:393-396); the client reader got a go token at connect and the paused test client never writes, so the reader is blocked in `read`, gets 0, and sends `Event::ClientEof`; `on_client_eof` (:919-926) sets `client_eof_seen` while Closing; `client_drained()` (:1190-1197) returns true through `|| self.client_eof_seen` before consulting `writer.is_finished()`. The `stop_reading` doc comment (:1555-1556, "its reader sees no EOF") is therefore wrong. The unguarded case is real code flow: `on_client` (~897-901) sets `client_idle = true` and returns while Closing, and `tick()` returns after `tick_closing` without calling `feed_client()`, so a reader parked on go_rx (client sent bytes during the drain, or was back-pressured by `may_read_source()` before Closing) never reads EOF, and only `writer.is_finished()` ends Phase A. An interactive terminal sending keystrokes during a live server-eof handoff is the ordinary way into that state. The seats confirmed from source and did not re-run the mutations.
  severity note: unanimous Nit. The product code is correct and removing both arms does fail the test; this is a regression-guard gap, not a defect. Kept at Nit, though it is the guard for the prior round's confirmed :1195 Should-fix, so a later refactor could reintroduce the grace-long stall with CI green.
  fix-shape hint: put the bridge's client reader into the parked state before the writer fails (have the test client write a chunk the bridge consumes after Closing(ServerEof) begins, with an observable edge before `stop_reading()`), fix the `stop_reading` doc comment, and confirm with the `is_finished` -> `false` mutation that the test fails.
