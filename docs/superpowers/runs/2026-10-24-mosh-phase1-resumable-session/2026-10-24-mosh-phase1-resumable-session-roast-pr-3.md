## Confirmed findings            ← consumed by super-design, one task per finding
- [Should-fix] src/mosh/local_bridge.rs:1195 — During the bridge's server-eof Closing drain, if the local client goes away while complete frames are still queued, nothing tells the Phase A drain wait that the client writer thread has exited. The connection stays in Closing until the remaining grace runs out (60 s default, up to 3600 s), and because the bridge serves one connection at a time, a restarted client waits unserved in the listen backlog for that whole time. [lanes: concurrency-async] (new)
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: `begin_server_eof` (local_bridge.rs ~1149-1167) sets `drain_until = now + params.grace` (or `down.give_up_at`); grace is clamped to 5..=3600 s (mod.rs:211-217). Phase A of `tick_closing` (~1183-1196) returns early on `!(self.client_drained() || now >= by)`. `client_drained()` (:1170) checks only `client_closed` or `client.written >= frames_end`; it never checks `client.writer.is_finished()`. The client writer thread (~850-866) breaks on the first write error (EPIPE after the peer is gone) and exits, so `written` stays below `frames_end`. `on_client_eof` (:904) and `on_client` (:883) both return early while `closing.is_some()`, so a ClientEof cannot set `client_closed`, and `tick()` returns right after `tick_closing`, so the reader is never re-armed. The only `writer.is_finished()` check is in Phase C (~1274), unreachable until Phase A exits. `start()` (~140-160) calls `serve_connection` inline in the accept loop, so no new connection is accepted until `finish()` returns. The keeper gets no final ACK meanwhile, so its session stays parked until its own grace. Design.md:486 bounds this drain by remaining grace for a slow but live client; it does not cover a client that is already gone, because "acks follow delivery" no longer holds once delivery cannot happen. The previous `close_client` at d49f3d93 (:1116-1135) looped on `!writer.is_finished()`, so it noticed a dead writer at once (reproduce seat; the refute and ground seats did not check the d49f3d93 comparison but confirmed the defect at head independently). None of the three existing server-eof tests disconnects the client mid-drain. Read from source by all three seats; not run.
  severity note: unanimous Should-fix. Bounded stall, not data loss; narrow trigger (client dies during a live server-eof handoff with frames queued). Kept at Should-fix under the low-blast-radius profile because the stall lands on the reconnect path the feature exists for, and it undoes a bound the previous code had.
  fix-shape hint: treat `client.writer.is_finished()` (or a ClientEof observed while Closing) as drained in Phase A, and add a server-eof test whose client disconnects mid-drain and asserts the connection closes within the stop budget rather than the grace.
